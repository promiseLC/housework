# 双人家务计酬前端 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在本工作树 `frontend/` 内实现完整的双人家务计酬首版 PWA：两人账号关联、家务按次定价与完工审核、线下付款后收款确认才结清，全部对接 OpenAPI 0.1.2 真实接口。

**Architecture:** 单页应用，Vite 开发服务器把 `/api/v1` 代理到 FastAPI。用 React Router 按登录 / 未关联 / 已关联（含解绑后只读历史）三层守卫路由；TanStack Query 的 queryKey 一律带 `userId` 与 `householdId`，登录、退出、切号时 `queryClient.clear()` 并清空令牌。金额只以整数分与后端交互，前端仅做「元」字符串的安全转换与展示。账务写操作禁止乐观成功、禁止离线排队；测试用 MSW 模拟接口，运行时不内置假账本。

**Tech Stack:** React 18 + TypeScript + Vite + React Router + TanStack Query + Ant Design Mobile + Vite PWA（Workbox）+ Vitest + Testing Library + MSW。

## Global Constraints

- 只改本工作树 `/workspace/household-pay/.worktrees/frontend` 内的计划文档和 `frontend/`；不修改 `docs/` 下已有产品/接口文档，不碰 `backend/` 源码，不改主工作树，不建远程、不推送、不部署。
- 对齐 `docs/backend/openapi.yaml` **0.1.2**，前缀 `/api/v1`；已登录请求带 `Authorization: Bearer <access_token>`。
- 登录注册使用 `username` + 密码，不做手机号或短信。
- 写资金或推进状态的 `POST` 必须带 `Idempotency-Key`（8–64 字符，一次点击/确认层生成 UUID，失败重试复用；用户发起新操作再换新键）。`POST .../payments/preview` 只读，不带幂等键、不占锁。
- 金额全程整数分；用户按「元」输入时转为分，不用浮点做入账或付款依据；应付合计与结算金额以后端字段为准。
- 成功前不把界面显示成已成功；确认完成、拒绝完工、标记已付款、确认已收款、拒绝到账成功后不提供撤销按钮。
- 待确认完工仅执行人可撤回为进行中（文案「撤回提交，继续做」），不是撤销审核。
- 邀请码：`GET /invites/current` 在 pending 且未过期时返回明文，刷新后仍可复制；`POST /invites/regenerate` 作废并生成新码；`DELETE /invites/current` 只作废不生成。
- 付款：勾选同方向整笔 `payable` 工资，提交前走 `POST /households/{householdId}/payments/preview`，按返回的对象、明细、`total_amount_fen` 核对后再创建；预览成功不保证创建成功，409 则重新预览。
- 解绑后旧历史只读，不得迁入新关系；有进行中（含撤回后）、待确认、已拒绝任务或待付款/待收款工资时禁止解绑。
- 三个主入口：家务 `/chores`、账本 `/ledger`、我的 `/me`。不接支付、不依赖推送。
- 账务写操作必须在线；无网提示「目前没有网络，账目需联网同步」，提供重试，不离线排队、不本地伪造已入账或已结清。
- UI：iPhone 竖屏单栏，主操作在下半部或底部，按钮高度 ≥ 44px，`viewport-fit=cover` 与安全区，状态用文字标签，金额大号清晰，无横向溢出。
- Git 作者使用「开发小组（本地开发）`<household-pay@localhost>`」；提交按 `docs`/`chore`/`feat`/`fix`/`test` 拆分，小提交。
- 时间按 Asia/Shanghai 展示；分页 `page` 默认 1、`page_size` 默认 20（最大 100）。

```ts
const FEN_MAX = 100_000_000

export function yuanStringToFen(input: string) {
  const raw = input.trim()
  if (!/^(?:0|[1-9]\d*)(?:\.\d{1,2})?$/.test(raw)) {
    return { ok: false as const, error: '请输入最多两位小数的正数金额' }
  }
  const [i, d = ''] = raw.split('.')
  const fen = Number(i) * 100 + Number(d.padEnd(2, '0'))
  if (!Number.isInteger(fen) || fen < 1 || fen > FEN_MAX) {
    return { ok: false as const, error: '金额须为正整数分，且不超过上限' }
  }
  return { ok: true as const, fen }
}

export function fenToYuanString(fen: number) {
  const sign = fen < 0 ? '-' : ''
  const abs = Math.abs(fen)
  return `${sign}${Math.floor(abs / 100)}.${String(abs % 100).padStart(2, '0')}`
}

export function formatFen(fen: number) {
  return `¥${fenToYuanString(fen)}`
}
```

## 实现时必须遵守的测试与数据原则

- 每个功能先写失败测试再写实现（TDD）。
- MSW handler 按状态机推进：例如 confirm 才创建 wage，preview 不改工资状态，创建付款才把工资改为 `awaiting_receipt`。禁止用静态「已全部结清」假数据冒充联调成功。
- 资金 mutation 一律 `await` 服务端结果再更新 UI；不要对工资/结算单做乐观成功。
- 切换账号、退出必须 `queryClient.clear()`，不能只 `invalidate`。

## 已发现的契约问题（前端按下列方式消化，不擅自改产品范围、不改 openapi.yaml）

1. **`GET /chore-types` 默认 `include_inactive=false`。** 产品要求列表含停用项。前端必须显式传 `include_inactive=true`。对齐稿写了「含停用项」但未写该查询参数。

2. **`GET /tasks` 的 `status` 只接受单个枚举**，一次不能请求「进行中+待确认+已拒绝」。前端对 worker 列表分次请求或省略 `status` 后过滤。不阻塞首版；若后端后续支持多值更好，但不在前端范围改契约。

3. **`PATCH /chore-types/{id}` 与 `DELETE /invites/current` 不要求 `Idempotency-Key`**（契约只强制写资金/推进状态的 POST）。前端按契约不带头，但仍防连点。交互稿把「编辑模板 / 作废邀请」列入幂等名单，以实现时跟 OpenAPI 为准。

4. **`DELETE /invites/current` 同时标注 `204`「已作废或本来没有」和 `409` Conflict**，未说明 409 条件。前端：204 视为成功并刷新；若返回 409 则展示 `message` 并重拉。

5. **`LedgerSummary.in_progress_count` 不在 required 列表。** 前端按可选处理，缺省不崩溃。

6. **`Wage.chore_name`、`PaymentItem.chore_name` / `task_id` 非必填。** 展示时有名称用名称，否则回退为「家务」+ 金额，不因缺字段白屏。

7. **解绑后 `GET /me.active_household` 为 null，但产品要求仍可只读查看旧账本。** 契约提供 `GET /households`（含已解绑）。前端用该列表建立只读家庭上下文，不能在解绑后把用户永久只留在 `/pair` 而无法看历史。

8. **`POST /auth/logout` 的 requestBody 未标 `required`，但 schema 是必填 `refresh_token` 的 `RefreshRequest`。** 前端注销时始终提交当前 refresh_token。

9. **`LoginRequest.username` 没有注册接口那套 pattern。** 前端登录不做过严字符集拦截，避免已注册账号被前端误拒；注册仍按契约校验。

10. **错误码只写在 `ErrorResponse` 的 description 里，`details` 无固定结构。** `UNBIND_BLOCKED` 不一定分类返回未完成事项。前端以可阅读的 `message` 为准，有 `details` 再补充展示。

11. **`listTasks` 的 `role=reviewer` 说明包含「我已审核的对方任务」。** 待我审核区必须再加 `status=pending_confirm`，避免把已确认/已拒绝混进待审核。

以上问题不改变已批准的产品流程，实现中按本计划消化；不向用户追加提问。

## 验收对照（实现完成后自检）

- 两账号数据按 queryKey 隔离，切号不串缓存。
- 模板改价不改已开始实例快照。
- 本人不能确认自身完工；待确认和已拒绝不计入应付。
- 标付款不是结清；仅收款人确认后才是已结清。
- 预览与创建竞态：409 后重新预览，不重复乐观入账。
- 双向债务不抵扣；金额为分。
- 邀请码刷新后仍能查看复制。
- 解绑拦截含撤回后的进行中任务；解绑后历史只读。
- iPhone 布局约束在 CSS/组件层落地；真机与实后端联调不在本次声称完成范围内。
